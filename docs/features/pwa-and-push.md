# PWA and push

Flick is a Progressive Web App. That means you can install it from the browser onto your phone or
computer, it opens like an app, it can show push notifications when it is closed, it accepts shared
text and links from other apps, and its shell opens even with no network. This page explains how each
part works, what is cached (and what is never cached) and how to test it. There is no AI in this area.
Status: Built. Real delivery on physical Android and iPhone devices cannot be proven from code.

### Back button in the installed app

In the installed app on a phone, the first Back press at the very start of the app shows "Press back again to exit"; a second Back within 2 seconds leaves. Other Back presses close dialogs, menus and the media viewer, or go from an open chat to the chat list. See [message-gestures.md](message-gestures.md). Needs a real device to confirm.

### App shortcuts and share target

Long-press the installed icon: **New chat** (`/people`), **Saved messages** (`/?saved=1`), **Calls**
(`/calls`). Sharing **text or a link** from another app to Flick opens `/share`, where you choose a
chat. Files and images cannot be shared in (the manifest declares text, title and url only). See
[integrations](integrations.md).

## Service worker (`src/pwa/sw.ts`)

- **precache:** the build output (JS, CSS, `index.html`, icons) so the app shell opens offline.
- **navigation:** page loads are answered with the cached `index.html`.
- **push:** parse the payload and always show a notification (a bad payload shows a generic one).
  Message notifications also get a **Reply** action on desktop Chrome and Edge.
- **notificationclick:** focus an open Flick window and tell it to open the chat, or open
  `/?c=<chat>&m=<message>&s=<seq>`. The app opens the chat and scrolls to the message
  (`openFromNotification.ts`). A typed Reply is passed as `?reply=` and placed in the message box; it is
  not auto-sent.
- **message `SKIP_WAITING`:** used by the update toast.

## What is cached, and what is not

| Cached                                   | Never cached                                       |
| ---------------------------------------- | -------------------------------------------------- |
| App shell: files in the build (precache) | Every API response (`/api/*` and any other origin) |
| `index.html` as the answer to page loads | Uploads and media                                  |
|                                          | The sign-in token (our code never stores it)       |
|                                          | Messages in the service worker cache               |

The worker has no runtime caching rule, so no API call, token or message can end up in its cache by
accident.

**Separate from the worker**, the app keeps a small "read offline" copy in IndexedDB: the chat list and
the last 50 messages of up to 30 recent chats. It is used only as a fallback when a fetch fails; live
data always wins. Settings > Storage > **Free up space** or **Clear local cache** removes it. Code:
`features/platform/offlineCache.ts`.

## Updates

Each deploy changes the file hashes. The new worker waits (`registerType: prompt`). The page shows
"A new version of Flick is available." with **Reload**. Nothing reloads by itself, so a chat is never
refreshed under you.

## Offline

- The shell loads from the cache. A connection banner shows the realtime state, and a pill says "You
  are offline. Flick will reconnect when you are back." from the browser's offline event.
- Signing in still needs the network (Clerk loads from the network). A cold offline start shows the
  notice and a loader, not the chat.
- Recent chats can open from the device copy above; sending waits in the outbox until you are back
  online. Calls need a network ([calls offline](calls-offline.md)).

## Push notifications

Push needs three things: the permission, a browser subscription, and the server's keys.

```
Settings switch or the install prompt
  1. GET /push/vapid-key       (null = server has no keys: switch disabled with an explanation)
  2. Notification.requestPermission()      (the first thing after the tap, a browser rule)
  3. pushManager.subscribe({ userVisibleOnly: true, applicationServerKey })
  4. POST /push/subscribe      (endpoint, keys, device, previews and quiet-hours choices)
Turning it off: POST /push/unsubscribe, then subscription.unsubscribe()
```

Keeping it working (`usePushLifecycle`): at app start, when the app returns to the front (not more
often than every 10 minutes) and when the browser replaces the subscription, Flick compares the browser's
subscription with the server's copy (`GET /push/status`) and repairs it. When you change message previews
or quiet hours it tells the server. After sign-out it drops this browser's subscription. A revoked
(signed-out) device is not pushed to. There is one subscription row per device.

| Platform         | Notes                                                                                                                                                      |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| iPhone and iPad  | Web Push works only in the Home Screen app (iOS 16.4 or newer). In a Safari tab, Flick says to add it to the Home Screen first and opens the install guide |
| Android (Chrome) | Works in the browser and the installed app; battery savers can delay pushes                                                                                |
| Desktop          | Chrome, Edge, Firefox. With the browser closed it works only while the browser process runs                                                                |

A friendly prompt card ("Turn on notifications so you never miss a message") appears once you have a chat
with a message. **Not now** hides it for a few days. The Settings panel shows "This device: On/Off" and
**Send me a test notification**. Full rules for who gets a push are in [notifications](notifications.md).

The server side: the worker signs pushes with VAPID keys (`VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`,
`VAPID_SUBJECT`); the API also needs the private key and subject for the test button. A 404 or 410 from
the push service disables that subscription.

## App badge

The installed app icon shows the unread count where the Badging API exists; the tab title shows "(3)
Flick" everywhere. See [notifications](notifications.md).

## Local testing

Service workers need HTTPS or `localhost`, and the dev server does not register one. Use
`npm run build -w @chat/web && npm run preview -w @chat/web`, then Chrome DevTools > Application >
Service Workers ("Push" sends a test payload).
