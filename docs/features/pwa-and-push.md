# Flick: installable app and web push

Code: `apps/web/src/pwa/` (service worker, install, update), `apps/web/src/features/notifications/`
(push subscribe, in-tab alerts) and `apps/web/src/features/settings/`.

## How a push reaches the browser

```
send message -> API (one DB transaction: message + outbox + pg-boss job "notify")
                                     |
 worker "notify" job: user offline and chat not muted?
        |  yes
        v
 web-push library, signed with VAPID keys
        |  HTTPS to the browser vendor's push service (FCM, Mozilla, Apple)
        v
 browser wakes the service worker  ->  "push" event  ->  showNotification(...)
        |
 user clicks  ->  "notificationclick"  ->  focus the open tab or open /?c=<conversation_id>
```

Payload (JSON, from `apps/worker/src/web-push-provider.ts`):
`{ title: sender name, body: short excerpt, conversation_id, message_id }`.

**Subscribing** (Settings > Notifications, only after a click):

1. The page loads the public key with `GET /push/vapid-key`. `null` means the server has no VAPID
   keys, so the switch is disabled with an explanation.
2. `Notification.requestPermission()`. If the user says no, nothing else happens.
3. `registration.pushManager.subscribe({ userVisibleOnly: true, applicationServerKey })`.
4. `POST /push/subscribe` with the endpoint and keys. Turning it off calls
   `POST /push/unsubscribe` and then `subscription.unsubscribe()`.

The permission prompt is the first thing that happens after the click (the key is fetched when
the page opens), because some browsers only allow the prompt right after a user gesture.

## What the service worker does (`src/pwa/sw.ts`)

- **push**: parse the payload, show a notification. The notification `tag` is the `message_id`,
  so if the worker retries and the push arrives twice, the second replaces the first.
  A bad payload still shows a generic "You have a new message".
- **notificationclick**: if a Flick window is open, tell it to open the conversation
  (`postMessage`) and focus it; otherwise `openWindow('/?c=<conversation_id>')`. The app reads
  `?c=`, waits for the chat list, then selects that conversation (`openFromNotification.ts`).
- **precache**: the build output (JS, CSS, `index.html`, icons) so the app shell opens offline.
- **message `SKIP_WAITING`**: used by the update toast.

## What is cached, and why

| Cached                                   | Not cached                                          |
| ---------------------------------------- | --------------------------------------------------- |
| App shell: files in the build (precache) | Every API response (`/api/*`, any other origin)     |
| `index.html` as the answer to page loads | Uploads and media                                   |
|                                          | The Clerk token (it is never stored by our code)    |
|                                          | Messages: only what is in memory while the app runs |

The worker answers **only** precached files and page navigations. It has no runtime caching
rule, so no API call, token or message can end up in a cache by accident. Each deploy changes
the file hashes; the new worker waits, the page shows "A new version of Flick is available",
and **Reload** activates it. A chat is never reloaded under the user.

Offline: the shell loads from the cache. The connection banner (realtime state) and an
"You are offline" notice (browser `offline` event) tell the user. Signing in still needs the
network because Clerk loads from the network, so a cold offline start shows the notice and a
loader, not the chat.

## Installing

`manifest.webmanifest` (name Flick, standalone, icons 192/512 and a maskable 512) is generated by
`vite-plugin-pwa` from `apps/web/vite.config.ts`. Icons are PNGs rendered from
`public/icons/icon.svg`. The browser fires `beforeinstallprompt`; we keep that event and show an
"Install app" button (navbar, Settings) that replays it. The button disappears after install.

## In-tab alerts (browser open, tab in the background)

`notifyIncoming` is called by the chat store for each new message. If the tab is hidden, the
message is recent (not catch-up after being offline) and the chat is not muted, it shows a
`Notification` (tag per conversation) and plays a short sound, at most once per second.
A muted chat still notifies when the message's `mentions` include the user. The sound is
generated with the Web Audio API, so there is no audio file. Both work only after permission is
granted, which happens when push is turned on.

## Local testing

Service workers need HTTPS or `localhost`, and the dev server does not register one. Use
`npm run build -w @chat/web && npm run preview -w @chat/web`, then Chrome DevTools >
Application > Service Workers ("Push" button sends a test payload).
